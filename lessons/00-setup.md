By the end you can run `uv run python -m game.app` and see a window, and

---

## Why `uv`

`uv` is a single tool that replaces `pyenv` + `venv` + `pip` + `pip-tools`. It:

- installs and pins the Python interpreter itself,
- creates and manages the virtual environment (`.venv/`),
- resolves and locks dependencies into `uv.lock`,
- runs commands inside that environment (`uv run ...`) without you ever
  activating anything.

You never type `pip install` or `source .venv/bin/activate` in this project.

Install it if you haven't: https://docs.astral.sh/uv/getting-started/installation/
(`curl -LsSf https://astral.sh/uv/install.sh | sh` on macOS/Linux).


This creates `pyproject.toml` (project metadata + dependency lists) and

## Step 2 — Add dependencies

```bash
uv add pygame-ce numpy
uv add --dev pytest ruff
```

- **`pygame-ce`** — "pygame community edition", an actively maintained fork of
  pygame. You still `import pygame` in code; the `-ce` is only the package name.
  It's our rendering + input + windowing layer.
- **`numpy`** — not used in Part A, but Parts B and C need it and adding it now
  keeps the lock file stable.
- **`pytest`** — test runner. `--dev` puts it in a dependency group that isn't
  installed when someone just wants to *play* the game.
- **`ruff`** — fast linter/formatter. We run it before each commit.

After this you'll have `uv.lock` and a `.venv/` directory. Both are managed by
uv; `.venv/` is git-ignored (check `.gitignore` — it's already there).

---

## Step 3 — Configure pytest and ruff

Open `pyproject.toml` and append:

```toml
[tool.pytest.ini_options]
pythonpath = ["."]
testpaths = ["tests"]

[tool.ruff]
line-length = 100
```

`pythonpath = ["."]` is the important line. Our packages (`battle_core/`,
`game/`) sit directly in the repo root, not under a `src/` directory. This tells
pytest to put the repo root on `sys.path` so `import battle_core` works from a
test file. (`uv run python -m game.app` already works without this, because
`python -m` adds the current directory to the path automatically.)

## Step 4 — Create the package skeleton

Make these directories and files.

`battle_core/__init__.py`:

```python
"""Pure-Python combat rules. No pygame, torch, numpy, or game/ imports allowed here."""
```

`game/__init__.py` — leave it completely empty (it just marks `game/` as a
package).

`game/app.py`:

```python
"""Entry point: window, clock, and (later) the scene stack."""
from __future__ import annotations

import pygame

WINDOW_SIZE = (800, 600)
BG_COLOR = (24, 24, 28)
FPS = 60


def main() -> None:
    pygame.init()
    screen = pygame.display.set_mode(WINDOW_SIZE)
    pygame.display.set_caption("AI RPG")
    clock = pygame.time.Clock()

    running = True
    while running:
        for event in pygame.event.get():
            if event.type == pygame.QUIT:
                running = False
            elif event.type == pygame.KEYDOWN and event.key == pygame.K_ESCAPE:
                running = False

        screen.fill(BG_COLOR)
        pygame.display.flip()
        clock.tick(FPS)

    pygame.quit()


if __name__ == "__main__":
    main()
```

What each part does:

- `pygame.init()` — brings up every pygame subsystem (display, font, event
  queue, ...).
- `pygame.display.set_mode(WINDOW_SIZE)` — creates the window and returns the
  **surface** you draw onto. A surface is just a 2D pixel buffer.
- `pygame.time.Clock()` — a frame-rate limiter.
- The **event loop**: `pygame.event.get()` drains the queue of everything that
  happened since last frame — key presses, mouse, the window's close button
  (`pygame.QUIT`). If you don't drain it, the OS thinks the app has hung.
- `screen.fill(BG_COLOR)` — paint the whole surface one colour. In a real frame
  you'd then draw sprites on top.
- `pygame.display.flip()` — swap the back buffer to the screen. Nothing you drew
  is visible until this call. (`flip` swaps the whole screen; `update` can swap
  just dirty rectangles — we use `flip` throughout, it's simpler.)
- `clock.tick(FPS)` — sleeps just long enough that the loop runs at most 60
  times per second, and returns the elapsed milliseconds (we'll use that return
  value as `dt` in Lesson 03).

## Step 5 — The import-isolation test

This is the most important test in the project. `battle_core/` is the rules
engine — the RL environment in Part C will `import battle_core` and drive it
millions of times during training. That only stays fast and portable if
`battle_core` never pulls in `pygame`, `torch`, `numpy`, or reaches sideways
into `game/`. This test fails the build if that boundary is ever crossed.

`tests/test_import_isolation.py`:

```python
"""battle_core must stay pure: no rendering or ML dependencies, no reaching into other app packages."""
import importlib
import pkgutil
import sys

import battle_core

FORBIDDEN = {"pygame", "torch", "numpy", "game", "rl", "dialogue"}


def test_battle_core_imports_nothing_forbidden():
    # Import every submodule of battle_core, then inspect what landed in sys.modules.
    for mod in pkgutil.iter_modules(battle_core.__path__, prefix="battle_core."):
        importlib.import_module(mod.name)

    leaked = {name.split(".")[0] for name in sys.modules} & FORBIDDEN
    assert not leaked, f"battle_core pulled in forbidden modules: {leaked}"
```

You'll also need an empty `tests/__init__.py`? No — pytest discovers `tests/`
without it thanks to `testpaths`. Just create the `tests/` directory with the
file above.

Run it:

```bash
uv run pytest tests/test_import_isolation.py -v
```

Expected: **1 passed**. (`battle_core` only has a docstring so far, so nothing
leaks.)
