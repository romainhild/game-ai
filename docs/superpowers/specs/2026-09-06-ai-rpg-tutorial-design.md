# AI RPG Tutorial — Design Spec

**Date:** 2026-09-06
**Status:** Approved for implementation planning

## 1. Purpose

A staged, hands-on tutorial that teaches the reader to build a small turn-based
RPG in which:

- **NPC dialogue** is generated by a large language model (Claude API by default,
  local model optional).
- **Enemy combat behaviour** is controlled by a reinforcement-learning policy the
  reader implements **from scratch** in PyTorch.

The reader is strong in Python and ML/PyTorch but new to game development and to
RL as a domain. The tutorial therefore moves quickly through ML fundamentals and
spends its depth on: game-loop architecture, framing combat as an MDP, reward and
observation engineering, a hand-written DQN, and integrating a trained policy back
into a real-time game.

## 2. Deliverable

- **`lessons/`** — numbered markdown lessons. Each contains: concept explanation,
  step-by-step build instructions, and a "what you can run now" checkpoint.
- **A single Python repo** that grows one checkpoint per lesson. Every checkpoint
  has green tests.
- **`design.md`** in the repo root — condensed architecture, the MDP spec, and the
  skill/stat data tables, so lessons stay reference-light.

The reader writes the code by following the lessons; the repo checkpoints are the
reference implementation.

## 3. Scope

**In scope**

- One playable turn-based battle system with skills, magic, MP, and status effects.
- One walkable town scene with 2–3 NPCs, collision, and a battle trigger.
- LLM dialogue with a swappable backend: `mock`, `claude`, `local` (Ollama).
- A from-scratch DQN (double + dueling refinements) training the enemy side.
- One shared policy controlling 1–3 enemies via egocentric observations.
- Training against a scripted player party with randomized composition; optional
  light self-play lesson.
- Integrating the trained checkpoint into the game with a heuristic fallback and a
  difficulty knob.
- Packaging with `pyinstaller`.

**Out of scope**

- Overworld map, multiple towns, quest lines, save-anywhere systems.
- PPO / actor-critic methods in the main path (flagged as follow-up only).
- Multi-agent RL frameworks (PettingZoo etc.) — flagged as follow-up.
- Networked / multiplayer anything.
- Art production — placeholder sprites and system fonts only.

## 4. Tooling & Dependencies

- **Python 3.11+**, project managed entirely with **`uv`**.
- `pyproject.toml` is the only dependency manifest. No `requirements.txt`.
- Commands: `uv run pytest`, `uv run python -m rl.train`,
  `uv run python -m game.app`.

| Purpose | Package | Group | Notes |
|---|---|---|---|
| Game | `pygame-ce` | default | maintained community fork; `import pygame` still works |
| RL | `torch`, `numpy` | default | CPU is sufficient; GPU optional |
| Env API | `gymnasium` | default | `Env` interface + spaces only |
| Plotting | `matplotlib` | `dev` | training curves |
| Dialogue (API) | `anthropic` | `dialogue` | official SDK; needs `ANTHROPIC_API_KEY` |
| Dev | `pytest`, `ruff` | `dev` | |
| Dialogue (local) | Ollama | — | external binary, not managed by `uv`; backend falls back to `mock` if unavailable |

Lessons 00–05 and all of Part C run fully offline on the `mock` backend. No API
key is needed until Lesson 06.

## 5. Architecture

### 5.1 Repo layout

```
game/
  pyproject.toml
  design.md
  battle_core/            # pure Python. No pygame, no torch. Source of truth for combat rules.
    entities.py           # Character, Skill, StatusEffect dataclasses + stat model
    skills.py             # data-driven skill/spell table and their effect functions
    battle.py             # BattleState: turn order, legal_actions(), step(action)->(state,events), is_over()
    heuristics.py         # scripted player party + scripted enemy (baseline / in-game fallback)
  rl/
    env.py                # Gymnasium-style wrapper around BattleState; reset/step/reward
    encoding.py           # BattleState <-> observation vector; action id <-> (skill,target); action mask
    dqn.py                # Q-network, replay buffer, target network, Bellman update (hand-written)
    train.py              # CLI: train enemy policy, write checkpoints/
    evaluate.py           # win-rate vs baselines; render sample battles
  dialogue/
    backend.py            # abstract LLMBackend (generate / stream)
    claude_backend.py     # Anthropic API (default)
    local_backend.py      # Ollama
    mock_backend.py       # canned responses; no network; used in tests and offline dev
    npc.py                # NPC persona + world facts + rolling memory; prompt assembly
  game/
    app.py                # pygame main loop + scene manager
    scenes/
      town.py             # tilemap, movement, collision, NPCs, "press E to talk", battle trigger
      battle.py           # HP/MP bars, action menu, target picker, message log; input -> battle_core
    policy_runtime.py     # load checkpoint, pick enemy actions in-game; fall back to heuristics
    assets/               # placeholder sprites, system font references
  tests/
  checkpoints/
  lessons/
```

### 5.2 The `battle_core` boundary

`battle_core` has no dependency on pygame or torch. Both the renderer and the RL
environment drive the *same* `BattleState` object — there is no second
implementation of the rules to drift out of sync.

`BattleState` public surface:

- `legal_actions(actor) -> list[Action]`
- `step(action) -> (BattleState, list[Event])` — advances one actor's turn
- `is_over() -> bool`, `winner() -> "player" | "enemy" | None`
- `current_actor() -> Character`
- Turn order resolved by speed stat; ties broken deterministically by side then slot.

`Event` objects (`Damage`, `Heal`, `StatusApplied`, `Faint`, `Miss`, ...) are what
the renderer animates and what the RL reward function reads. State is otherwise
plain data.

### 5.3 Combat as an MDP

- **Agent identity:** a single shared policy controls the entire enemy side. On
  each enemy's turn, `encoding.py` builds *that enemy's* egocentric observation and
  the same network is queried. Parameter sharing — scales from 1 to N enemies with
  no code change.
- **Observation:** fixed-size `float32` vector:
  `[ self stats+status, ally slots (fixed count, zero-padded), foe slots (fixed
  count, zero-padded), global turn counter ]`. All stats normalized. Egocentric
  ordering (self first) so one network generalizes across enemy slots.
- **Action space:** discrete id over `(skill × target) + {defend}`. Fixed maximum
  (~25). An **action mask** (`bool` vector) marks legal choices given MP and living
  targets. The mask is applied both at action-selection time and inside the DQN
  loss (illegal next-state actions excluded from the max).
- **Reward:**
  - Terminal: `+1` enemy victory, `-1` enemy party wipe.
  - Shaping (small, tunable, off by default in the "pure" config):
    `+k1 * (fraction of player-party HP removed this step)`,
    `-k2` per turn (anti-stall), with `k1, k2` small (~0.1, ~0.01).
  - Lesson 09 deliberately sets shaping too high to demonstrate reward hacking,
    then dials it back.
- **Opponent:** scripted player party (`heuristics.py`) with randomized levels and
  composition each episode. Lesson 13 (optional) swaps in a frozen weak checkpoint
  for light self-play.
- **Episode:** one battle. Hard turn cap (e.g. 60) → treated as player win
  (enemies failed to close it out).

### 5.4 RL algorithm

Hand-written **DQN** in PyTorch:

- MLP Q-network (2–3 hidden layers).
- Uniform replay buffer, ε-greedy exploration with linear decay.
- Target network with periodic hard update.
- Refinements added in Lesson 11: double DQN (decouple action selection from
  evaluation) and a dueling head (value + advantage streams).
- Prioritized replay mentioned as optional, not required.
- PPO is named as the natural follow-up in Lesson 15 but is not implemented.

Rationale: discrete actions, short episodes, small state — the canonical
"implement your first RL algorithm" setting. From-scratch DQN is tractable to get
correct and to read.

### 5.5 Dialogue subsystem

- `LLMBackend` abstract base: `generate(prompt) -> str` and
  `stream(prompt) -> Iterator[str]`.
- `mock_backend` — deterministic canned lines keyed by NPC id; used by all tests
  and by offline development.
- `claude_backend` — Anthropic SDK; model id and params pulled from the current
  Anthropic API reference at implementation time.
- `local_backend` — Ollama HTTP API; falls back to `mock` if Ollama is not
  reachable.
- `npc.py` — holds per-NPC `persona` string, a short list of `world_facts`, and a
  rolling memory of the last few exchanges (fixed turn budget, oldest dropped).
  Assembles the prompt; parses an optional structured "start battle" signal from
  the reply.
- **Seams with combat:** an NPC may trigger a battle; the post-battle result is
  fed back as one line of context for the next conversation. Nothing else couples
  the two subsystems.

## 7. Testing Strategy

- **`battle_core` — tested hard.** Every skill, status effect, turn-order edge
  case, and win/lose condition. This is the contract both other subsystems depend
  on.
- **RL code — smoke tests, not accuracy tests.** Replay buffer semantics, mask
  correctness, tensor shapes, "loss decreases on a fixed batch", "agent beats a
  do-nothing opponent within N episodes". Policy quality is measured by
  `evaluate.py` win-rate curves, not asserted in unit tests.
- **Dialogue — tested against `mock_backend` only.** Prompt assembly, memory
  truncation, persona injection, "start battle" parsing. Never hits the network.
- Every lesson checkpoint ships with green tests.

## 9. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| DQN training unstable / never converges | Small fixed enemy/player rosters first; sparse reward + tiny shaping; double DQN; evaluation harness from Lesson 11 to catch regressions early |
| pygame friction dominates for a game-dev newcomer | Part A lessons keep rendering minimal (rects, bars, text); no asset pipeline; `battle_core` is testable without a window |
| Anthropic SDK / model ids drift from training data | Implementation of Lesson 06 pulls model id, params, and streaming API from the current Anthropic API reference, not from memory |
| Reward hacking produces degenerate policies | Explicitly taught in Lesson 09 with a worked example and fix |
| Scope creep into overworld / quests | Section 3 out-of-scope list is explicit; town is a single scene with a battle trigger |
| Trained enemy is unfun (too strong / too random) | Lesson 14 difficulty knob (inference temperature / ε) and heuristic fallback |
